# fiftybox-local 레인 풀 설계

날짜: 2026-10-22
상태: 승인됨 (2026-10-22)

## 목적

`fiftybox-local`이 독립 태스크를 맥스튜디오와 ioh PC에 나눠 동시에 실행하게 한다. 목적은 전체 소요 시간(벽시계 시간) 단축이다.

지금은 `fiftybox-local`만 부르면 태스크가 전부 맥스튜디오 Flash-Next로 간다. ioh-control의 RAG 코드를 고칠 때 사용자가 매번 «ioh의 q3s도 써»라고 따로 지시해야 했다. ioh의 `iq3s`는 `--executor iq3s`로 쓸 수 있지만 한 번에 한쪽만 고르고, 스킬 문서상 사용자가 지시했을 때만 쓴다.

두 PC는 서빙하는 모델이 다르고, 어느 한쪽이 꺼져 있을 때도 있다. 특히 ioh는 RAG 때문에 q3s를 내리고 gemma4 12b를 올리기도 한다. 그래서 분배는 «지금 살아 있는 쪽만 쓰고, 중간에 죽으면 다른 쪽이 받는다»를 지켜야 한다.

## 현재 구조 (바뀌는 이유)

- 태스크를 한 줄로 순차 실행한다. executor는 하나로 고정이다(`fbl_task.py`의 `EXECUTORS` 표에서 `--executor`로 하나를 고른다).
- 모든 태스크가 작업 폴더 하나를 공유한다. 검사(SCOPE·TAMPER·DIFF)는 태스크 전후로 폴더 전체의 스냅샷을 찍어 비교한다. 두 태스크가 같은 폴더에서 동시에 돌면 스냅샷에 서로의 변경이 섞인다.
- 테스트 명령은 작업 폴더 전체에서 돈다. 다른 태스크의 Red 테스트가 폴더에 있으면 실패한다.
- `orchestrate.py --phase implement`는 artifact 디렉터리의 `summary.json`이 가리키는 worktree 하나만 안다.

## 목표

1. 시작할 때 레인마다 서버가 살아 있는지 확인하고, 살아 있는 레인만 풀에 넣는다.
2. 독립인 태스크를 레인이 동시에 하나씩 가져간다. 한가해진 레인이 다음 태스크를 가져간다. 번호로 미리 나누지 않는다.
3. 실행 중 레인이 죽으면 그 태스크를 다른 레인이 이어받는다. 다른 레인이 이미 일하고 있으면 큐 뒤에 넣는다.
4. 결과 줄과 메트릭에 어느 레인이 했는지 남는다.
5. 살아 있는 레인이 하나뿐이면 지금과 같은 순차 실행이다.

## 비목표

- ioh의 gemma4 12b는 executor가 아니다. 레인 표에 넣지 않는다.
- ioh의 Qwen3.8 27B는 GPU 추가 뒤의 일이다. 이번에 코드를 만들지 않는다. 다만 레인 표에 한 줄을 더하면 들어갈 수 있는 구조로 한다(레인마다 자기 예산을 가진다).
- 맥스튜디오 안에서 모델 둘을 동시에 돌리지 않는다. Flash-Next가 램 약 75GB를 써서 같은 맥의 27B·Gemma4와 램을 다툰다. 레인은 PC 한 대에 하나다.
- 서버를 올리거나 내리지 않고 모델을 바꾸지 않는다. ioh는 아예 건드리지 않는다. 스튜디오의 기존 기동 절차(`reference.md`)는 그대로다.
- 유료 모델이나 원격 무료 모델로 전환하지 않는다. 풀에는 로컬 레인 둘만 있다.
- 실행 예산 상수(70/15/2/14/140)를 바꾸지 않는다.
- 오케스트레이터가 구현 파일을 직접 쓰지 않는다는 금지는 그대로다.

## 반대 목표

다음은 동작하면 실패다.

- ioh에서 모델을 올리거나 내린다. RAG가 ioh를 쓰는 중에 이 스킬이 방해한다.
- ioh가 RAG 때문에 내려갔다고 다시 올리려 한다.
- 두 레인이 같은 파일을 동시에 고친다.
- 같은 태스크가 두 레인에서 동시에 돈다.
- 죽은 레인이 반쯤 고친 파일이 남은 채로 다른 레인의 작업이 시작되거나 합쳐진다.
- 독립이라고 선언되지 않은 태스크를 동시에 돌린다.

## 사용자가 정한 것

- 목적은 시간 단축이다.
- 레인은 PC 한 대다. 맥스튜디오는 Flash-Next oQ4e-mtp, ioh는 `qwen3.8-flash-next-iq3_s`다.
- ioh가 gemma4를 올리면 Tailscale로 응답하지 않는다(그렇게 설정해 둠). 그래서 레인이 살아 있는지는 서버 응답 여부로 판단한다. 모델 이름 확인은 필요 없다.
- q3s가 RAG 때문에 내려가면, 그걸 인식한 시점에 q3s가 하던 일을 맥스튜디오 모델이 이어받는다. 맥스튜디오가 이미 일하고 있으면 큐에 넣는다.

## 제 판단으로 정한 것 (읽으면서 확인해 주세요)

- **이어받기는 처음부터 다시 하는 것이다.** 모델은 세션 기억이 없고 반쯤 고친 파일은 믿을 수 없다. 이어받기 전에 그 태스크가 죽은 레인에서 바꾼 것을 버린다.
- **이동 조건은 서버 문제뿐이다.** 분류가 `server`(연결 거부, 도중 EOF, 502, 헬스 응답 없음)일 때만 다른 레인으로 옮긴다. `timeout`·`no_changes`·테스트 실패는 옮기지 않는다. 기존 규칙(`timeout`은 쪼개기 등)을 따른다.
- **이동은 재시도 예산(태스크당 1회)을 쓰지 않는다.** 인프라 장애이지 모델 실패가 아니기 때문이다. 태스크당 이동은 1회로 제한한다. 두 레인이 다 죽으면 `STOP`하고 사용자에게 보고한다.
- **방향은 대칭이다.** 사용자는 ioh→스튜디오를 말했지만, 스튜디오가 죽으면 ioh가 받는 것도 같은 규칙이다.
- **죽음을 알아채는 쪽은 `fbl_task.py`다.** Claude가 아니다. 스킬의 «사용량 계약»(폴링 금지, 오케스트레이터 턴 최소화) 때문이다. Claude는 결과 줄(`MOVED=`)과 최종 보고에서 알게 된다.
- **독립 선언은 `Depends:` 줄이다.** 태스크 명세에 `Depends: 1,2` 또는 `Depends: none`을 쓴다(오케스트레이터가 Step 3에서 쓴다). 줄이 없으면 앞선 모든 태스크에 의존하는 것으로 본다(=순차, 안전한 기본값). 동시에 돌 수 있는 조건은 `Depends:`가 충족됐고, `Modify ONLY:` 파일이 지금 돌고 있는 태스크와 겹치지 않는 것이다. Red 테스트 파일도 겹치지 않아야 한다.
- **병렬은 자동이다.** 살아 있는 레인이 둘 이상이고 준비된 태스크가 둘 이상일 때 켜진다. `--lanes flash-next`처럼 레인을 지정하면 그 레인만 쓴다.
- **레인마다 작업 폴더가 따로다.** 각 레인이 자기 git worktree에서 구현·테스트·검사를 한다. 검사를 통과한(`CLEAN`) 태스크의 소유 파일만 메인 작업 폴더에 합친다. 소유 파일이 겹치지 않으니 충돌이 없다. `FLAG`·`FAIL` 변경은 합치지 않는다. 의존하는 태스크가 시작될 때는 레인 폴더를 합쳐진 메인 상태에 맞춘다.
- **둘 다 한가하고 준비된 태스크가 하나뿐이면 스튜디오가 가져간다.** 양자화가 더 높고 컨텍스트가 더 크기 때문이다.
- **레인당 동시 태스크는 하나다.** 한 서버에 요청 둘을 겹치지 않는다.
- **메트릭과 `calibrate`는 레인별이다.** `iq3_s`는 `oQ4e`보다 양자화가 낮아 성공률이 다를 수 있다. `executor-metrics.md`에 레인 열을 더하고, `ADVICE`도 레인별로 낸다. 상수 조정은 기존처럼 사용자 승인 뒤에만 한다.
- **리뷰는 지금처럼 묶음당 1회다.** diff는 합쳐진 메인 작업 폴더 기준이다.
- **출력 줄에 `LANE=`을 더하고, 이동이 있었으면 `MOVED=flash-next->iq3s`처럼 표시한다.**
- **스킬 문서를 고친다.** «executor 고정»은 «레인 풀(표에 있는 레인만)»로, «ioh는 사용자 지시 때만»은 삭제한다. 실행용 사본 `~/.claude/skills/fiftybox-local`을 repo 사본과 맞춘다. 지금 실행용 사본에는 ioh 컨텍스트가 옛 값 65,536으로 남아 있다(repo는 131,072).

## 빌더에게 맡기는 것

- 동시 실행 방식(스레드, 서브프로세스), 큐 구조.
- 레인 worktree를 만들고 정리하는 방법, 파일을 합치는 방법. `orchestrate.py`는 artifact 디렉터리의 `summary.json`이 가리키는 worktree 하나만 읽으므로, 레인마다 별도 artifact 디렉터리를 두는 방법과 `orchestrate.py`를 고치는 방법 중 쉬운 쪽을 고른다.
- 레인 표를 둘 위치와 형식(`EXECUTORS` 확장).
- `--detach`·`wait`·`status` 출력과의 호환.
- 테스트 방법. 가짜 디스패처로 레인 사망을 재현한다.

## 성공 기준

- 독립 태스크 4개, 레인 둘 정상: 두 레인에서 동시에 돌고, 총 시간이 순차 합보다 짧다.
- ioh가 응답하지 않을 때: 오류 없이 스튜디오 단독으로 지금과 같은 결과가 나온다.
- 실행 중 ioh가 죽을 때: 그 태스크가 스튜디오에서 처음부터 다시 돌아 `CLEAN`이 되고, 재시도 예산이 소진되지 않고, 결과 줄에 `MOVED=`가 나온다.
- 스튜디오가 이미 일하는 중에 ioh가 죽을 때: 이동한 태스크가 큐 뒤에서 기다렸다 실행된다.
- `Depends:`가 없거나 `Modify ONLY:`가 겹치는 태스크는 동시에 돌지 않는다.
- 두 레인이 다 죽으면 `STOP`과 사유가 나오고, 반쯤 고쳐진 파일이 메인 작업 폴더에 남지 않는다.
- 기존 단일 레인 동작과 테스트가 그대로 통과한다.
